# Этап 6: документы, поиск и управляемая память

Статус: **завершён 28 октября 2026**, включая контейнерную и живую приёмку двух итераций. Итог ниже; прежние записи остановок сохранены как история. Данные этапа 5 на другой установке автоматически не переносились.

## Границы

Документы PDF с текстовым слоем, DOCX, Markdown/TXT служат доказательствами. Табличные датасеты остаются входами вычислений, поиск не заменяет Python/SQL. OCR, изображения, embeddings/reranking и свободный конструктор страниц — отдельные расширения. Сначала получаем измеряемый полнотекстовый RAG и воспроизводимые цитаты. Исходные документы не могут менять системные инструкции или права агентов.

## Порядок работ и критерии

### 6.1. Контракты, хранение и очередь

- Document принадлежит проекту, имеет неизменяемые DocumentVersion и указатель текущей версии. Версии хранят имя, SHA256, размер, оригинал, состояние queued/processing/ready/failed/deleted, ошибку и версию pipeline.
- Повтор загрузки с client_id и тем же содержимым возвращает прежнюю версию; другой payload с этим ключом даёт конфликт. expected_revision защищает замену от конкурирующих правок. Изменение указателя и очередь обработки — одна транзакция.
- DocumentChunk содержит стабильный ID, исходные элементы/координаты, путь заголовков, тип, текст и хеш, порядок и версию chunker. PostgreSQL — каноническое хранилище, полнотекстовый индекс перестраивается из канонических фрагментов.
- Миграция 0007 аддитивная, сохраняет существующие цели/Run/ML. Обработка документов не зависит от ENABLE_MODEL_CALLS и не использует ключ модели.
- Проверки: миграция с 0006, изоляция проектов, replay/conflict, потеря worker и повтор задачи без дублирования чанков. Ограничены размер оригинала, распаковка DOCX, извлечённый текст, число страниц/чанков и время парсера.

### 6.2. Парсеры и чанкинг

- Сначала извлечь элементы, затем разбить слишком большие элементы готовым splitter. Заголовки/списки/абзацы и таблицы сохраняют связь с источником. Для Markdown — заголовки и номера строк; DOCX — блоки/заголовки/строки таблиц (номера страниц без надёжного источника не выдумываются); PDF — страницы и явно обозначенные ограничения извлечения.
- Маленькие таблицы целиком; большие — группами строк с повторением заголовка. У больших текстовых элементов небольшой overlap; раздельные разделы не смешиваются. Соседний контекст читается отдельно, без бесконтрольного расширения выдачи.
- Начальные границы задаются по символам, явно не называются токенами. При подключении embeddings учитывается tokenizer именно embedding-модели и меняется версия chunker; старые цитаты сохраняются.
- Кандидаты: Docling HybridChunker, Unstructured, лёгкие парсеры и langchain-text-splitters. Выбор фиксируется после оценки форматов, координат, ресурсных требований и контрольных примеров. В первой поставке допустим ограниченный парсер с явными предупреждениями; нельзя объявлять восстановленную структуру PDF точной без проверки.
- Проверки: русский/английский текст, длинный раздел, определения на границе, таблица с единицами, пустой/сканированный/повреждённый PDF, DOCX zip bomb, стабильность ID и повтор после прерывания.

### 6.3. Поиск, чтение и UI

- Project-scoped API загрузки, списка версий, статусов, повтора failed-задачи, удаления, поиска и чтения чанка с соседями. Явный исторический поиск; по умолчанию только текущие ready-версии. Совпадения из memory и прежних результатов сохраняют тип/статус и происхождение.
- Поиск по заголовкам и тексту с PostgreSQL FTS, русской/английской лексикой; ранжирование воспроизводимо, число и длина результатов ограничены. Никакого смешивания клиентов/проектов.
- Во вкладке файлов отдельная область документов: загрузка, обработка/ошибка, версии, поиск, источник и скачивание оригинала. UI объясняет неполноту извлечения; текст отображается как текст, не исполняемый HTML.
- Проверки: релевантный фрагмент, отсутствие ответа, историческая версия, одинаковый текст в разных проектах, отсутствующий оригинал, фильтры и API; build frontend. Визуальная проверка только затронутого сценария при доступном сервере.

### 6.4. PM, специалисты и фиксируемый контекст

- Общие инструменты search_knowledge/read_source. PM сохраняет квитанции операций и цитирует версию/чанк; вопрос не запускает исследование. Результат поиска — источник, не утверждение истинности.
- GoalSpec получает явные выбранные document sources (version/chunk/hash/reason). При создании Run копируются выбранные доказательства и manifest: содержимое и координаты остаются доступны после обновления оригинала/перезапуска. Новые роли/инструменты выпускаются в новой версии профиля, старые профили не меняются.
- Специалисты ищут в закреплённых версиях Run, сохраняют полученные источники в контексте/квитанциях. Независимый evaluator читает те же точные доказательства; найденный текст сам не даёт approval расчёту.
- Проверки: PM-вопрос без Run, scoped tool call, чужая ссылка/подменённый хеш, замена документа во время Run, совпадение снимка после рестарта, legacy v1/v2/v3 профили.

### 6.5. Актуальность и жизненный цикл

- Замена документа не переписывает прежние фрагменты/цитаты; предыдущая версия помечается исторической. Использующие её источники и Run получают вычисляемый признак актуальности, без изменения старых verdict.
- Новая версия определения не становится автоматически истинной заменой прежнего: агент сравнивает точные цитаты и сообщает противоречие. Память различает пользовательское утверждение, документный источник, гипотезу и независимо проверенный результат.
- Удаление исключает документ из живого поиска и удаляет оригиналы/индекс/кеши; сохранённые снимки Run отдельно обозначаются как исторические доказательства и показываются в отчёте об удалении. Полное стирание должно явно учитывать эти копии; нельзя обещать стирание всех копий при сохранённых frozen Run.
- Проверки: обновление/удаление во время обработки, устаревание контекста, повтор удаления, отсутствие воскресших чанков после retry, публикации не переписываются.

### 6.6. Оценка retrieval и приёмка

- Локальный синтетический набор на RU/EN: определение метрики, таблица/единицы, две противоречащие версии, вопрос без источника, нерелевантный документ и межпроектная утечка. Сохраняются ожидаемые источники и результаты поиска.
- Измерить попадание ожидаемого источника в top-k, корректность версии/цитаты, отсутствие утечек и задержку. Порог первого набора: все детерминированные контрольные вопросы находят ожидаемый фрагмент в top-5, отрицательные/межпроектные проверки проходят; это регрессия, а не оценка качества на всех документах.
- Решение об embeddings/reranking принимается по отдельному набору перефразировок: расходы и лимиты независимы от chat-модели; индекс можно перестроить. При отсутствии измерений не объявлять гибридный поиск реализованным.
- Сквозная приёмка: загрузить методику → PM находит/цитирует определение без исследования → анализ сохраняет источники → заменить методику → новая итерация замечает различие → перезапуск сохраняет обе версии и доказательства. Большая часть проверок без модели; отдельный платный прогон только при необходимости и в ранее согласованном бюджете.

## Поставка и контроль

Каждый шаг сопровождается нужными API/UI/тестами; частичный этап помечается частичным в хэндофе. Не запускать полный набор повторно без новых изменений. Актуальный порог пользователя: **15% оставшейся пятичасовой квоты**; недельная квота не является условием остановки. При пороге сохранять изменения, выключать платные вызовы и фиксировать незавершённое. Чужие сервисы и старый paused Run sonder не трогать. Полный этап считается готовым только после пунктов 6.1–6.6; локальные parser/FTS-тесты не заменяют живую приёмку.

## Реализовано 28 октября

Ветка `codex/documents-rag`, база изменений — `543099f`. Миграция `0007` добавляет документы, версии, чанки, lease и GIN-индекс, а также документное происхождение памяти. Старый текст памяти сохраняется; нормализованное поисковое представление backfill-ится отдельно. Идентичность версий, чанки и документные доказательства Run защищены от UPDATE в БД. Миграция upgrade/downgrade проверена на отдельной PostgreSQL-БД.

Загрузка оригинала и постановка обработки фиксируются вместе с версией. client_id защищает повтор загрузки, expected_revision — конкурентную замену. Незавершённую обработку можно повторить по lease; три прерывания подряд требуют явного retry. Ошибка парсера, изменение оригинала и удаление во время обработки не создают ready-результат. Проверены rollback после вставки чанков и два конкурирующих обработчика. Удаление проекта учитывает новые таблицы и защищённые от записи файлы.

Выбраны лёгкие адаптеры `pypdf==6.21.3` и `python-docx==1.1.2`, готовый `langchain-text-splitters==1.1.3`. Собственного алгоритма разрезания длинного текста нет: RecursiveCharacterTextSplitter делит объединённые соседние абзацы внутри раздела/страницы по естественным границам, с размером тела 2400 символов и overlap 160. Заголовки и таблицы обрабатывает адаптер структуры; заголовок таблицы повторяется у строк. Полный фрагмент с контекстом ограничен 6500 символами. Это **не токены** embedding-модели. Pipeline с версиями библиотек сохраняется у версии документа.

Docling/Unstructured не установлены и не объявлены победителями сравнительного теста. Для первого объёма выбраны доступные парсеры и готовый splitter; Docling следует отдельно оценить на документах со сложной вёрсткой, где его структурный разбор может дать преимущество. PDF в текущей поставке сохраняет страницу и текст/layout, **не гарантирует восстановление таблиц и порядка чтения**. DOCX сохраняет body-блоки/строки таблиц, не выдумывает страницы; колонтитулы, text boxes и прочие нетекстовые/вне-body материалы не индексируются. Для Markdown сохраняются заголовки/строки, для фрагментов — исходные элементы и смещения. Оригинал доступен для проверки.

Парсер работает в отдельном процессе с таймаутом 60 с и без DB/model/executor credentials. В Linux выставляются RLIMIT_AS 1 GiB и RLIMIT_CPU 45 с; на Windows эти системные ограничения не проверялись и не выставляются. Ограничены размер оригинала (20 МиБ), распакованного DOCX (30 МиБ), текст (2 млн символов), PDF (500 страниц/10 МиБ content stream на страницу), чанки (5000). OCR отсутствует; пустое извлечение даёт видимую ошибку. Ingestion не вызывает модель: usage отдельно хранит время/чанки и `model_calls=0`, `api_cost=0`.

Полнотекстовый поиск использует PostgreSQL Russian/English/simple и Unicode casefold поискового представления; исходный текст/хеш не меняются. По умолчанию выдаются текущие ready-версии, доступны исторические и точная версия. Чтение возвращает точный фрагмент, SHA256, координаты, предупреждения и до двух соседей в каждую сторону. Поиск включает атрибутированную память и метаданные прежних результатов, сохраняя их статус/ограничения. Эмбеддингов и reranking нет.

PM получил `search_knowledge`/`read_source`, квитанции и цитирование; документный вопрос не создаёт Run. `document_statement` требует сохранённого read_source и точной цитаты. После замены/удаления версии такие записи памяти остаются в истории, но исключаются из актуальной памяти и обычного поиска. Это рабочая память о содержимом документа, а не независимое одобрение вывода.

Новые Run используют профиль ролей **v4**; v1/v2/v3 сохраняют исходные инструменты/промпты. GoalSpec.document_sources содержит точные chunk/version/hash/reason. Выбранный текст фиксируется в project_context, task/project-context.json и отдельных immutable task/document-source-N.txt; при восстановлении проверяется хеш. Полученные исследователем поисковые фрагменты/прочитанные источники сохраняются как immutable document_evidence в Run. Удаление живого документа не переписывает эти доказательства; API удаления явно сообщает об оставшихся Run и истории PM. Полное удаление проекта отдельно убирает его историю и файлы.

Область документов фиксируется при сообщении PM/создании Run: до 200 ready-версий, в видимом контексте только индекс первых 20 без длинных warnings. Полная выбранная область остаётся в manifest/снимке. `document_scope` сообщает размер, лимиты и возможное отсечение; при большом архиве нужны явный выбор источников и дальнейшее развитие пагинации/выбора области. Новые документы не подменяют источники уже работающего Run.

UI во вкладке «Файлы» позволяет загрузить/заменить документ, увидеть версии и ошибки, повторить обработку, скачать оригинал, искать и открыть цитату с соседним контекстом. Удаление объясняет сохранение исторических копий. Прокрутка/общая вёрстка из TODO не перерабатывались.

### API

- `GET/POST /api/projects/{project}/documents`: версии / multipart file, client_id, expected_revision, optional document_id.
- `GET /api/projects/{project}/documents/versions/{version}/original`.
- `POST /api/projects/{project}/documents/retry`: version_id.
- `DELETE /api/projects/{project}/documents/{document}`: expected_revision; ответ содержит retained_run_ids и описание сохранённых исторических копий.
- `POST /api/projects/{project}/knowledge/search`: query, kind documents/memory/results/all, optional version_id, include_historical, limit 1..10.
- `GET /api/projects/{project}/knowledge/sources/{source}`: chunk:UUID, memory:UUID или result:RunID:ResultID; neighbors 0..2.

### Первоначальный остаток приёмки (закрыт итогом ниже)

1. Контейнерная сборка и проверка Linux-парсера/фонового ingestion с restart worker: Docker Engine на этой машине был недоступен. Локальные PostgreSQL-тесты lease/rollback и child parser этого полностью не заменяют.
2. Отдельная контролируемая живая приёмка новой документной цепочки: PM → методика → анализ с зафиксированными источниками → новая версия → сопоставление/объяснение противоречия. В этом проходе платная модель не включалась; это нельзя обозначать как завершённую живую приёмку.
3. Расширить контрольный набор на реальные RU/EN документы и перефразировки, измерить задержку/ошибки извлечения; после этого решить, нужны ли Docling, embeddings и reranker. Они не являются автоматически обязательными зависимостями первой поставки.

Следующие UX-возможности, большой архив/пагинация, полное стирание отдельных документов вместе с каждой исторической копией и OCR требуют отдельного объёма. Текущее удаление документа не называется полным стиранием; удаление целого проекта имеет отдельный сценарий.

Исправлено: binding сообщения включает уже загруженные queued/processing/failed версии и их статус, поиск позже читает готовую закреплённую версию. Это не добавляет документы, загруженные после сообщения. Новый регрессионный тест и два затронутых сценария прошли. Дополнительно проверена актуальность Run sources при замене методики: API возвращает отдельное source_freshness, applicable становится false, прежний verified verdict сохраняется.
