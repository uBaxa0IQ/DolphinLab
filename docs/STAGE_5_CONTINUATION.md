# Этап 5: продолжение и проверка с настоящей моделью

## Сохранённые источники следующей итерации

GoalSpec.prior_results содержит явный выбор: run_id, result_id, SHA256 и причину использования. PM получает ограниченный индекс результатов прежних запусков и сохраняет выбор вместе с новой версией цели. Упоминание названий в вопросе не заменяет ссылки. Интерфейс показывает выбранные версии в условиях цели.

Сервер проверяет проект, завершённое состояние исходного Run, точный хеш и отсутствие повторных ссылок. При создании Run фиксируются выбранные ревизии, статусы проверки, assessment и версии входов. Применимость к текущим файлам отмечается отдельно; определения и границы вопроса всё равно нужно проверить. Исходное доказательство копируется в task/prior-result-N.json с повторной проверкой SHA256. Полный manifest остаётся в project-context.json, в системную постановку попадает только индекс.

Историческая проверка не присваивает approval новой работе. Реестр нового Run по-прежнему содержит собственные ревизии: при необходимости специалист использует сохранённые prepared views в своём source job, а evaluator проверяет новые утверждения. Прямой импорт старого результата со всеми его зависимостями и verdict в новый реестр не добавлен. Публикации прежних запусков читаются через выбор Run и версии страницы.

## Бюджет и восстановление

Режим enforce_request_limits включает локальный порог текстового ввода и max_tokens на стороне API. Вход оценивается по UTF-8 JSON с запасом на сообщения и схемы; это не точный tokenizer. До вызова резервируются текущий ввод и весь разрешённый выход по верхним тарифам с запасом. Разные запросы имеют разные резервы; параллельное завершение освобождает только собственную сумму. При неизвестном исходе резерв считается потраченным.

provider_cost_currency разрешает учитывать usage.cost только после явного подтверждения валюты. Некорректные, отрицательные и бесконечные значения не используются. Без подтверждённой суммы действует прежний расчёт по токенам/резерву. Старый журнал расходов не пересчитывается. PM имеет отдельный накопительный бюджет проекта; Run хранит исходный тариф и лимит.

Слишком дорогой запрос блокирует своего агента, сохраняя возможность более дешёвых действий координатора. После остановки по бюджету доступно явное продолжение того же Run: сервер проверяет характер ошибки, отсутствие другого активного запуска и исходный deadline. Цель, inputs, policy и уже выполненные jobs не меняются. Истёкший запуск требует новой итерации с выбранными результатами. Смена подключения/тарифа останавливает клиента до следующего запроса.

Лимит текущего запуска можно явно изменить через «Изменить лимит» или PUT /projects/{project}/runs/{run}/budget. Операция сохраняет новую ревизию лимита и событие, требует expected_revision и client_id; исходный policy остаётся снимком. Снижение ниже оплаченного и активных резервов, неизвестный тариф, чужой Run и изменение истёкшего запуска отклоняются. Агенты не получают инструмента изменения денежного лимита. Возобновление остановленного Run выполняется отдельно.

Проверки отчёта покрывают каждый объявленный критерий. Уникальные явные обозначения C1:, C2: и т. п. служат стабильными идентификаторами; C1 не совпадает с C10, неоднозначный повтор ID требует точного текста. Для критериев без ID сохраняется точное сопоставление имени. Отсутствующие критерии перечисляются в ошибке публикации. Требования к независимости, исходным jobs и проверкам всех зависимостей сохранены.

## Исправления, найденные живым прогоном

- Executor возвращает версии библиотек объектом; контекст сериализует его корректно.
- Executor получает группу 1000 для доступа к manifest в общем volume без расширения capabilities или доступа к секретам backend. Задание запускается от UID 65534.
- Значения CPU/RAM по умолчанию укладываются в выделенные ресурсы Run; явное превышение остаётся ошибкой.
- Постановка различает analysis, ML и mixed; аналитика не требует фиктивного submission.csv. Точные JSON-схемы результатов доступны в task/result-schemas.json.
- PM явно передаёт параметры суммы/фильтра и выбор prior_results. JSON-строка во вложенном goal декодируется с последующей полной проверкой GoalSpec; лишние поля и права не принимаются.
- В обзоре скрыты технические heartbeat/usage-события, сохранив их в журнале и SSE. Аналитическая сводка не требует выбора ML-метрики.

## Воспроизводимые проверки

Backend: `PYTHONPATH=backend/src python -m unittest discover -s backend/tests -v` с отдельной TEST_DATABASE_URL базы с суффиксом `_test`. Проверяются exact references, project scope, повреждение доказательств, материализация после перезапуска, изоляция бюджетов, разные параллельные резервы, восстановление после бюджетной ошибки, неизменность scope и регрессия ML. Модель этими тестами не вызывается.

Проверка настоящего executor без модели, из PowerShell при запущенной платформе:

```powershell
Get-Content -Raw scripts/smoke_executor.py | docker compose --env-file .env.docker.local exec -T worker python -
```

Создаётся отдельная синтетическая папка executor-check-* в runs volume. Проверяются сумма CSV 330000, UID 65534, отсутствие OPENAI_API_KEY в задании, повтор отправки launch и чтение прежнего результата без второго запуска.

Живой сценарий использует Qwen qwen3.8-27b через RouterAI и четыре вымышленные строки. PM ответил 170000 за сентябрь без создания исследования. Техлид выбрал аналитика и evaluator, затем сам добавил редактора. Расчёты дали 160000 → 170000 RUB и рост 6,25%; блоки получили независимые assessments. Проверены пауза, перезапуск worker и сохранность четырёх уже выполненных jobs по ID, состоянию, хешу кода и timestamps. Точный итог публикации и расход фиксируются после окончания контролируемого прогона; офлайн-проверки не заменяют этот результат.

Документы/RAG, сложные страницы команд и свободный конструктор интерфейса остаются последующими этапами. Этот этап не публикует релиз в GitHub.
