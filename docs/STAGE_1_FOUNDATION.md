# Первый этап: цели и история исследований

Реализован фундамент итеративного проекта. Исследовательский runtime пока использует существующие ML-роли и правила проверки кандидатов.

## Что доступно

- Каждый проект получает начальную версию цели. Новая версия сохраняет вопрос, ожидаемые результаты, определения, ограничения и открытые вопросы.
- Во вкладке «История» можно подготовить итерацию без включения модели, увидеть её цель, связь с предыдущей итерацией и запуски.
- Изменение цели создаёт новую запись. Существующий Run сохраняет прежнюю постановку; новая цель относится к следующим запускам.
- Новый запуск использует подготовленную последнюю итерацию с текущей целью либо создаёт новую. Явный `iteration_id` позволяет выбрать сохранённую постановку.
- Resume продолжает тот же Run и итерацию. Новая попытка исполнения может быть связана с той же итерацией явно.
- Повтор команды с тем же client ID возвращает исходную запись; изменение содержимого под тем же ID отклоняется. Запись сериализуется на уровне проекта, проверяются базовые версии и область проекта.
- Изменение задачи через прежнее окно настроек также создаёт версию, сохраняя остальные условия цели.

Связь итераций в этой версии сохраняет происхождение работы. Автоматическая передача межитерационной памяти и результатов агентам будет добавлена следующим этапом. Аналитические отчёты, динамические роли и RAG пока не включены.

## Обновление

Миграция `0003` добавляет цели и итерации, связывает каждый старый Run с его собственной сохранённой задачей и отдельно сохраняет актуальное описание проекта. Исходные task_description, inputs, policy, connection, расходы, публикации и checkpoints не переписываются.

Обновлять API и worker вместе после остановки записывающих процессов и создания резервной копии, как описано в [DEPLOYMENT](DEPLOYMENT.md). Старый API не должен продолжать создавать Run после применения новой схемы. В рамках разработки миграция проверена на синтетической БД 0.1; пользовательские volumes не мигрировались автоматически.

## HTTP-контракты

- `GET /api/projects/{id}/goals` — версии цели, новые первыми.
- `POST /api/projects/{id}/goals` — `client_id`, `expected_revision`, `goal`.
- `GET /api/projects/{id}/iterations` — итерации с постановкой и запусками.
- `GET /api/projects/{id}/iterations/{iteration_id}` — одна итерация в области проекта.
- `POST /api/projects/{id}/iterations` — `client_id`, `expected_sequence`, `goal_revision_id`, `parent_iteration_id` последней итерации либо null.
- `POST /api/projects/{id}/runs` — необязательные `client_id` и `iteration_id`; старый вызов без тела остаётся допустимым.

Создание цели и подготовка итерации не требуют ENABLE_MODEL_CALLS. Запуск вычислений сохраняет действующие проверки подключения, бюджета, ресурсов и разрешения вызовов модели.

## Проверки без API модели

Используется стандартный `unittest`; тестовый worker и LLM-клиент не запускаются. Доменным проверкам не требуется PostgreSQL. Интеграционные проверки используют только явно заданный `TEST_DATABASE_URL`; имя базы должно оканчиваться на `_test`.

Интеграционные тесты пересоздают схему `public` указанной тестовой БД. Использовать отдельный временный PostgreSQL, не базу рабочего проекта.

Пример PowerShell из корня проекта:

```powershell
$env:PYTHONPATH = 'backend/src'
python -m unittest discover -s backend/tests -v

# Для полного набора задать URL отдельной одноразовой БД:
$env:TEST_DATABASE_URL = 'postgresql+psycopg://test_user:test_password@127.0.0.1:55432/dolphinlab_test'
python -m unittest discover -s backend/tests -v
```

Проверяются миграция legacy-снимков/checkpoints, неизменяемость целей, конкурентные записи, идемпотентность, изоляция проектов, архивирование/удаление, связь Run, pause/resume, сохранность при новом соединении и HTTP-контракты. Отдельно проверен браузерный путь создания проекта, изменения цели, подготовки итераций и чтения истории после перезагрузки.
