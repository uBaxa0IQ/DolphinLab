# Проектирование исследовательского пространства 0.2

Статус: проектные решения для реализации. Дата: 27 октября 2026 года.
Документ уточняет [дорожную карту](../ROADMAP_0_2.md). Описанные сущности и инструменты пока не являются возможностями работающей версии.

## 1. Основной пользовательский цикл

1. Пользователь описывает вопрос и добавляет данные/документы. PM сопоставляет запрос с известным контекстом проекта.
2. PM задаёт только вопросы, ответы на которые меняют расчёт, смысл результата, доступные ресурсы или критерий готовности. Предположения и открытые вопросы видимы пользователю.
3. Формируется версия цели. Явное поручение начать работу в согласованных границах достаточно для запуска; отдельное ритуальное подтверждение каждого шага не требуется.
4. Техлид составляет план и выбирает исполнителей. Специалисты регистрируют промежуточные результаты, проверяющий фиксирует выводы проверки.
5. Пользователь получает постепенно наполняемый отчёт и объяснения PM. Черновики и проверенные части различимы.
6. После завершения пользователь задаёт следующий вопрос. Создаётся связанная итерация, которая получает выбранные результаты прошлого исследования и доступ к архиву.

При недостатке данных возможен полезный итог: явно установленные ограничения и список недостающих материалов. Не считать отсутствие доказанного эффекта технической ошибкой. Технический успех исполнения, полнота поставки и ответ на исследовательский вопрос учитываются раздельно.

## 2. Границы сущностей и неизменяемость

### Project и постановка

`Project` содержит постоянную идентичность пространства, разговор, настройки, источники и указатели на текущую цель/публикацию. Статус проекта является представлением его работы; технический lifecycle принадлежит Run.

`GoalRevision` содержит `project_id`, номер версии, формулировку вопроса, ожидаемые результаты, определения метрик, допущения, ограничения, открытые вопросы и ссылки на пользовательские сообщения. Изменение создаёт новую запись. Статус согласования/замены фиксируется отдельным решением, а не перезаписью исходной постановки.

Договорённость с пользователем и предположение PM различаются по происхождению. PM не помечает собственное предположение как согласованное без основания в сообщениях или действующей политике пользователя.

### Iteration и Run

`Iteration` ссылается на GoalRevision, родительскую итерацию и зафиксированный набор используемых ResultRevision. Имеет план, критерии поставки, общий бюджет, состояние и итоговую оценку полноты.

`Run` сохраняет конкретное исполнение: снимки политики, входов, модели/провайдера, ролей, инструментов и версий контрактов. В одной итерации допускаются последовательные попытки; они имеют разные Run ID и общий учёт расходов. Перезапуск процесса, повтор доставки команды и resume после паузы продолжают прежний Run.

Для 0.2 действует один активный Run на проект и существующее ограничение worker. Следующая итерация может обсуждаться во время исполнения, но её вычисления ожидают доступного слота. Структура связей допускает будущие ветки; интерфейс 0.2 показывает линейную историю.

### Результат и его проверка

`Result` — стабильная идентичность логического результата; `ResultRevision` — точное содержимое и зависимости версии. Файлы связываются через зарегистрированные Artifact, а не произвольный путь, переданный агентом.

`Artifact` содержит область проекта/Run, тип содержимого, размер, хеш, место хранения и исходный job. Тип результата определяет обязательные поля: таблица — схему и данные, график — спецификацию и data view, вывод — утверждение и доказательства.

`Assessment` — добавляемая запись проверки конкретной версии: reviewer session, метод, verification jobs, заключение, область проверенного утверждения и ограничения. Переоценка дописывает историю. Текущий статус вычисляется с учётом действующих проверок и блокеров.

Автор исходного результата не может подтвердить его независимой проверкой. Evaluator владеет собственным verification job: это ожидаемая часть проверки, а не авторство исходного результата. Разные сессии и задания обеспечивают процедурное разделение; научная корректность всё равно требует реальных доказательств.

### Публикация

`PageRevision` хранит структуру и точные версии блоков. `PublicationRevision` фиксирует опубликованную PageRevision и manifest зависимостей. Черновик может обновляться, опубликованная версия воспроизводится по сохранённым ссылкам.

Проверенный расчёт и текстовая интерпретация имеют отдельные ссылки и проверки. Добавление нового объяснения к проверенному графику не делает объяснение автоматически подтверждённым.

## 3. Состояния и изменения направления

У итерации разделяются:

- подготовка: draft/clarifying/ready;
- исполнение: idle/queued/active/awaiting_input/closed;
- поставка: none/partial/delivered;
- итог: answered/inconclusive/cancelled/technical_failure, с текстовым объяснением.

Эта детализация заменяет укрупнённую схему итерации из первоначальной дорожной карты. В БД хранить только независимые измерения; производные состояния UI вычисляются в presenter. Состояния Run сохраняют существующий смысл.

Сообщение во время активной работы получает один из маршрутов:

- **Вопрос о ходе работы:** PM отвечает по сохранённым фактам.
- **Уточнение в пределах цели:** создаётся decision/directive, адресованный текущей итерации и Run.
- **Изменение существенного определения или ожидаемого результата:** новая GoalRevision и явная поправка плана; ранее полученные результаты не переписываются.
- **Новый самостоятельный вопрос:** готовится следующая итерация.
- **Pause/stop/finish/resume:** прямой управляющий канал с проверкой текущего состояния, без ожидания LLM.

Неясный маршрут PM уточняет. У directive есть явный адресат, состояние доставки и решение исполнителя. Истечение Run не превращает старое поручение в команду следующему исследованию. Частично выполненные поручения передаются в handover с их реальным состоянием.

Длительное ожидание ответа пользователя отражается как awaiting_input с сохранением состояния. Расход времени и поведение текущих jobs следуют явной политике паузы; PM не обещает остановку бюджета до фактической остановки исполнения.

## 4. Роли: владелец, инструменты и результат

### PM

Владеет постановкой и диалогом. Читает состояние, документы и результаты, создаёт проекты версий цели и направляет согласованные поручения. Не исполняет исследовательский код и не присваивает проверенный статус.

Выход: понятная пользователю постановка, объяснение текущего состояния, сохранённые договорённости и подготовленная следующая итерация.

### Техлид

Владеет стратегией исследования и общим планом. Выбирает компетенции, создаёт/меняет команды и назначения, распределяет ресурсы, принимает решения о продолжении направлений и разбирает противоречия. Проверенные статусы берёт из registry.

Выход: объяснимый план, назначения, решения о портфеле вопросов и итоговая оценка того, что удалось установить. Выполнение кода делегируется специалистам.

### Тимлид

Владеет вопросом конкретной команды, её синтезом и передачей результатов. Ведёт структуру командной страницы через разрешённые инструменты. Не обязателен для одного специалиста: тогда supervisor назначения — техлид.

### Аналитик данных

Строит расчёты и аналитические гипотезы, выбирает методы, создаёт таблицы и спецификации графиков, регистрирует утверждения. Исполняет Python в своей области и публикует результаты в registry. Не меняет оригиналы источников и не одобряет собственные выводы.

### Data engineer и ML engineer

Data engineer создаёт воспроизводимые версии подготовленных данных и проверяет преобразования. ML engineer отвечает за модель, оценочные артефакты и точное inference. Оба используют общий контракт результатов и существующий executor.

### Evaluator

Проверяет конкретные утверждения и версии результатов. Может читать исходные данные, запускать собственную проверку, фиксировать ограничения, противоречия и блокеры. Проверяющий может обслуживать несколько небольших направлений; отдельный экземпляр в каждой команде не обязателен.

Проверка выбирается соразмерно утверждению. Для описательной статистики не требуется тот же процесс, что для причинного вывода или качества модели. При этом формат файла и успешный exit code не заменяют проверку содержания.

### Редактор исследования

Владеет композицией главной страницы и её понятностью. Выбирает нужные результаты, группировку, подписи и интерактивность, проверяет предпросмотр. Собственные интерпретации регистрирует как утверждения с источниками.

Редактор не изменяет расчёты и статусы проверки. При противоречии сохраняет видимость расхождения и создаёт запрос на разбор техлиду. Он может появиться после первых результатов; постоянное потребление LLM в ожидании не требуется.

### Профиль и сессия

`RoleProfileRevision` задаёт назначение, разрешённые инструменты, области записи, структуру контекста и обязанности. Runtime проверяет capability и область объекта при каждой операции. Новая формулировка роли не расширяет разрешения.

`AgentSession` фиксирует профиль, итерацию, назначение, supervisor и epoch. Продолжение проекта не требует сохранять бесконечно растущую сессию каждого специалиста. Новая сессия получает релевантный handover; оригиналы прежней работы доступны через память.

Происхождение связывает сессию с устойчивым actor/assignment ID. Смена роли или epoch тем же исполнителем не позволяет представить свою работу независимой проверкой. Замена исполнителя и передача авторства отражаются в журнале, исходное авторство сохраняется.

Минимальное назначение: аналитик + независимый reviewer; техлид организует работу, редактор собирает итог по мере готовности. Дополнительные роли и команды добавляются с объяснением ожидаемой пользы, ресурсов и границ вопроса.

## 5. Память: жизненный цикл знания

Новая запись содержит текст/структуру, автора, область, источники, версии данных и состояние утверждения. Память различает решение пользователя, определение из документа, рабочую гипотезу, наблюдение и проверенный вывод.

Жизненный цикл:

1. Специалист сохраняет наблюдение с результатом расчёта и зависимостями.
2. Оно становится доступно связанным назначениям как сообщённый результат.
3. Evaluator добавляет проверку; общая память отражает проверенный статус в пределах описанных условий.
4. Новая версия данных/определения или блокирующая проверка отмечает затронутые знания как требующие пересмотра.
5. Историческая версия и её доказательства остаются доступны для воспроизведения.

Смена рабочего датасета не делает неверной историческую справку о предыдущем датасете. Актуальность оценивается относительно текущего вопроса и условий применения. Зависимости пересчитываются адресно, без глобального сброса всех знаний.

Приоритет рабочей памяти: активные ограничения и поручения, блокеры, проверенные применимые знания, открытые вопросы, затем вспомогательные материалы. Популярность записи или частота её повторения не повышает достоверность.

Противоречия хранятся явными связями. Сжатие истории сохраняет обе версии, основания и состояние разбора. Глобальное резюме не является единственным экземпляром памяти проекта.

Архивирование удаляет объёмные материалы из рабочего контекста, сохраняя оригиналы. Удаление по запросу пользователя является отдельной операцией с обработкой файлов, индекса, кешей и зависимостей; политика сроков хранения определяется настройками пространства.

## 6. Сборка контекста и RAG

`ContextService` получает роль/назначение, версию цели, текущую итерацию и допустимые источники. Сначала добавляет обязательные факты из структурированного состояния, затем доказательства и найденные материалы, затем последние целые обмены.

До поиска применяются project scope и доступ. После поиска учитываются версии, период, статус проверки и применимость к данным. Поиск по точному идентификатору результата выполняется напрямую. Смысловой запрос использует retrieval.

Результат поиска содержит краткий фрагмент, идентификатор/версию источника, координаты, причину соответствия и возможность открыть соседний контекст. Балл релевантности не является уверенностью в истинности текста.

Для задачи «перечислить все риски в отчёте» одного набора наиболее похожих фрагментов недостаточно: нужен план чтения с покрытием разделов и сохранённым состоянием обработки. Отсутствие фрагмента в выдаче не доказывает отсутствие факта в документе.

В `ContextManifest` сохраняются обязательные версии, запросы, фильтры, найденные ссылки, отобранные фрагменты и ссылки на архив обменов. Ключи модели и другие секреты туда не входят.

Обязательная цель, прямые управляющие команды и действующие лимиты не зависят от успешности семантического поиска. При недоступном индексе доступны структурированное состояние, чтение известных источников и явное сообщение об ограничении поиска.

Начальный индекс: текстовые документы, определения, решения, findings и handover. Сырые строки больших таблиц и все хвосты логов по умолчанию не индексируются как знания. Схемы/описания помогают найти данные, расчёт выполняется инструментом.

Первый retrieval использует полнотекстовый поиск и фильтры PostgreSQL. Embeddings и reranking подключаются через адаптеры после проверки на контрольных вопросах. Контракт поиска не зависит от выбранного движка. Смена embedding-модели создаёт новую версию индекса; разные пространства embeddings не смешиваются.

## 7. Страницы, графики и интерактивность

Главная навигация: исследование, данные/источники, история итераций и команды. Детали jobs и расходов доступны по раскрытию. Центральный экран выбирает структуру под цель: аналитический рассказ, сравнение гипотез или ML-результат.

Для 0.2 страница является деревом разрешённых блоков. Блок имеет стабильный ID, тип, позицию, ссылку на ResultRevision и настройки представления. Тема, допустимые компоновки и адаптивность задаются приложением.

Аналитик регистрирует график; тимлид добавляет его в страницу команды; редактор включает конкретную версию в общую страницу. Простое назначение может передавать результат напрямую редактору.

Командная страница принадлежит команде; публикация главной — редактору. Агент не перезаписывает страницу другой команды. Пользовательские закрепления и правки имеют владельца и сохраняются при новой сборке.

`ChartSpec` хранит версию схемы приложения, тип/кодировки, data view revision, подписи, единицы, период, агрегации и доступные взаимодействия. Data view подготовлен job и имеет схему/хеш. Спецификация библиотеки строится или валидируется разрешённым адаптером.

Фильтр по уже подготовленным данным работает локально без LLM. Фильтр, требующий нового расчёта, создаёт запрос и новую версию результата. UI показывает состояние подготовки и не подменяет предыдущий график пустым блоком.

Верхнеуровневые изменения страницы применяются с `expected_revision`. При конфликте агент получает актуальную версию и пересобирает только затронутые изменения. Все опубликованные версии сохраняются, восстановление прежней создаёт новую публикацию с её manifest.

Предпросмотр выполняется тем же renderer, что используется пользователем. Проверяются рендер, переполнение, подписи, легенды, размер данных, клавиатура и узкий экран. В дальнейшем можно добавить визуальную инспекцию редактором; в первом сценарии достаточно автоматической проверки renderer и ручной приёмки.

## 8. Транзакции, восстановление и бюджеты

Канонические сущности и неизменяемые версии хранятся в PostgreSQL, файлы — в volumes. Текущие указатели и статусы являются обновляемыми представлениями. Полное event sourcing не требуется; журнал изменений и устойчивые идентификаторы операций обязательны.

Команда изменения имеет ключ идемпотентности в области проекта и типа операции. Повтор с тем же ключом/содержимым возвращает исходный результат; повтор ключа с иным содержимым отклоняется. Изменение состояния и outbox-задание фиксируются в одной транзакции.

Фоновый обработчик подтверждает выполненный эффект; при сбое сверяет состояние по стабильному ID. Для model/tool/executor используются существующие checkpoints, receipts и идентичность процессов. Новый тип инструмента обязан описать способ сверки или явно возвращать неизвестный исход.

Публикация файлов проходит подготовку, проверку хеша и фиксацию manifest. Незавершённая подготовка восстанавливается или очищается фоновым согласованием. Пользователь продолжает видеть предыдущую согласованную публикацию.

Бюджеты: проект задаёт общие ограничения; итерация — исследовательский объём; Run — конкретное исполнение. Разговор PM и ingestion имеют отдельные категории расходов и настроенные пределы. Резервирование идёт через общий ledger, чтобы параллельные роли не превышали суммарный лимит.

Повтор, пауза, смена роли и новая сессия не обнуляют расходы. Задания редактора, сжатие контекста, embeddings и reranking учитываются. Консервативная оценка неизвестного запроса остаётся видимой.

## 9. Разделение модулей при реализации

- `domain`: контракты целей/итераций/результатов и правила переходов/проверки.
- `application`: команды, запросы и транзакции; операции PM, страниц и продолжения.
- `research`: назначения, роли, команды, координация и handover.
- `knowledge`: сборка контекста, источники, retrieval и правила применимости — через явные порты хранилища/поиска.
- `infrastructure`: PostgreSQL, ingestion, поисковые адаптеры, файлы и model/executor clients.
- `api`: HTTP-контракты, SSE и presenters.
- `frontend/features`: цели/история, источники, результаты, страницы, команды и разговор.

Это направления ответственности; новые каталоги создаются вместе с работающим сценарием. Не переносить весь существующий runtime ради соответствия схеме каталогов.

## 10. Совместимость 0.1 и первый внедряемый объём

Миграции добавляют сущности и связывают существующие Run с legacy-итерациями. Исходные снимки задачи, inputs, пути, checkpoints и publication не переписываются. Legacy ML-publication читается через адаптер общего результата.

Отсутствие документированной проверки в старом результате не превращается в новую проверку при миграции. Старые agent sessions продолжают использовать сохранённый профиль; переключение протокола активного Run требует явного механизма и не входит в первую миграцию.

Первый внедряемый объём: один проект, одна активная итерация, PM/техлид, аналитическое назначение, evaluator, редактор, несколько типов графиков, линейное продолжение и структурированная память без embeddings. Это проверяет основной цикл и оставляет действующий ML-путь доступным.

## 11. Открытые решения и способ их принять

- **Модель embeddings и reranker:** выбрать по контрольному набору русских/английских документов, стоимости и ограничениям размещения.
- **Размеры фрагментов:** подобрать по структуре документов и retrieval-оценкам; таблицы и определения проверять отдельно.
- **Хранение больших data views:** начать с файловых артефактов и ограниченных представлений API; измерить объёмы и задержку до выбора дополнительного движка.
- **Порог разделения ролей:** оценить пользу отдельного визуализатора и дополнительных тимлидов на одинаковых задачах с учётом расходов.
- **Глубина проверки:** определить policy по типам утверждений; тестовые примеры должны включать заведомо ошибочные выводы.
- **Экспорт отчёта:** первым сделать воспроизводимый пакет manifest/данных; формат пользовательского PDF/HTML выбрать по первым отчётам.

Ни одно открытое решение не блокирует первый аналитический цикл с ограниченным набором контрактов. Результат выбора фиксируется отдельным ADR с условиями пересмотра.

## 12. Работа с ветками

`main` хранит выпуски, `dev` — интеграцию следующей версии. Feature/fix/chore-ветки создаются под небольшой законченный объём и удаляются после слияния и проверки, что нужные изменения доступны в целевой ветке. Незамерженная работа сохраняется.

Release/hotfix-ветки удаляются после выпуска и синхронизации изменений в `dev`. Релизные теги и постоянные ветки сохраняются. Локальное удаление использует проверку слитых изменений; force-delete и переписывание опубликованной истории не являются обычной частью процесса.

Завершение CI/публикации 0.1 ведётся отдельно от проектирования 0.2 и не блокирует работу над документацией и изолированными контрактами.
