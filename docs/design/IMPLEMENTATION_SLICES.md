# Первые задачи разработки и сценарии приёмки 0.2

Статус: план реализации, не отчёт о выполненных изменениях.
Связанные документы: [проектирование](RESEARCH_WORKSPACE.md), [дорожная карта](../ROADMAP_0_2.md).

## Порядок разработки

Работать законченными сценариями: контракт → операция → хранение → представление → проверка. Сохранять рабочий ML-путь на каждом этапе. Новые инструменты агента включаются только вместе с runtime-проверкой полномочий и способом восстановления.

Первый контрольный результат — два связанных аналитических исследования с реальными расчётами и отчётами, переживающие перезапуск. Первый RAG-индекс и сложная компоновка страниц следуют после этого результата.

## Задача 1. Контракты и проверочные данные

**Объём:** типы ссылок, версии цели, критерии результата, идентичность итерации/Run, происхождение артефактов и минимальная проверка утверждения. Контракты чистые, без обязательного импорта БД или LLM-клиента.

**Изменяемые области:** `backend/src/dolphinlab/domain/`, новая область тестов и синтетические fixtures. Версии протоколов и поля, необходимые для будущего сохранения, задаются явно.

**Проверить:** результат нельзя связать с другой областью проекта; версия положительна; ссылка на файл и точная версия результата различимы; reviewer исходного результата не совпадает с его автором; состояние проверки не смешивается с готовностью и актуальностью.

**За границами:** миграции, агентные промпты, изменение UI и запуск настоящих моделей.

**Готовность:** тесты правил контрактов выполняются локально без ключа, Docker и внешней сети. Проверки поведения модели пока не подменяются этими тестами.

## Задача 2. Сохранённая цель и история итераций

**Объём:** аддитивные миграции Project/GoalRevision/Iteration, привязка Run, журнал решений, API создания/чтения истории и простое представление в UI.

**Изменяемые области:** модели/миграции, application-сервис итераций, API/schemas/presenters, frontend types/API и небольшой компонент истории.

**Проверить:** повтор команды с одинаковым ключом возвращает прежнюю запись; несовпадающий payload отклоняется; параллельные изменения версии обнаруживаются; старая GoalRevision неизменна; область проекта проверяется на стороне сервера.

**Миграция:** старые Run получают legacy-связь без изменения исходных inputs, policy, checkpoints и файлов. Legacy-цель выводится из сохранённого снимка задачи, а не из сегодняшнего описания проекта.

**Готовность:** создание и чтение истории работает после перезапуска API; копия БД старой версии обновляется без потери ссылок. Подключение живых клиентских volumes в тестах не используется.

## Задача 3. PM уточняет цель и маршрутизирует продолжение

**Объём:** работа PM с постановкой, назначением сообщения и draft следующей итерации. Подключить сохранённые договорённости к текущему LangGraph-процессу PM.

**Изменяемые области:** `agents/project_manager.py`, application messages/iterations, сборщик обязательного контекста и статусы UI чата.

**Проверить:** вопрос о ходе работы не создаёт вычислительное задание; явное поручение в действующих границах не требует повторной формальной кнопки подтверждения; существенная неоднозначность метрики даёт вопрос пользователю; новое исследование не изменяет snapshot активного Run.

**Восстановление:** связать сохранение решения/директивы и событие транзакцией. Повтор исходного сообщения и восстановление checkpoint не создают дубликат поручения.

**Готовность:** детерминированный model adapter проходит сценарии уточнения, запуска и продолжения; расход разговорной сессии видим и ограничен политикой.

## Задача 4. Память проекта и назначений

**Объём:** записи решений, определений, утверждений и handover с источниками/версиями. Структурированное чтение по ID и полям, первый ContextService и ContextManifest.

**Изменяемые области:** доменные контракты, application/knowledge-сервис и порты, PostgreSQL-адаптер, интеграция с существующей памятью Run.

**Проверить:** обязательные ограничения присутствуют при пустом поиске; резюме не меняет статус гипотезы; предыдущая итерация доступна по явным ссылкам; противоречие не исчезает при сжатии; архив читается после закрытия команды.

**За границами:** embeddings, отдельная векторная БД, автоматический GraphRAG и полная загрузка архива в контекст.

**Готовность:** новая сессия получает цель, ограничения, применимые результаты и открытые вопросы из сохранённого состояния, а не из process-local переменных.

## Задача 5. Роли, назначения и состав команды

**Объём:** RoleProfileRevision, AgentSession/Assignment, разрешения инструментов и выбираемый состав. Сначала перенести существующие роли, затем добавить аналитика и редактора.

**Изменяемые области:** `research/roles.py`, `tools.py`, `teams.py`, runtime dispatch и сохранение профиля исполнения.

**Проверить:** подмена имени роли в arguments не даёт прав; аналитик не присваивает проверенный статус; менеджеры не запускают Python; редактор не пишет чужие результаты; evaluator может создать собственное проверочное задание.

**Состав:** один специалист может работать напрямую под техлидом. Команда с несколькими специалистами получает тимлида по необходимости. Reviewer назначается с учётом независимости и нагрузки; свободный проверяющий может обслужить несколько направлений.

**Готовность:** простой анализ и ML-задача получают разный набор специалистов; завершение назначения сохраняет handover; лимиты ресурсов и числа активных агентов соблюдаются.

## Задача 6. Реестр результатов и минимальный отчёт

**Объём:** Artifact/ResultRevision/Assessment, prepared data views, таблицы/метрики/findings/charts, простая PageRevision и публикация. Legacy ML-candidate читается через совместимый адаптер.

**Изменяемые области:** registry и инструменты регистрации/проверки, application/API результатов, executor-контракт файлов и frontend-renderer.

**Проверить:** ссылки указывают на зарегистрированные артефакты нужного проекта; хеш проверяется при фиксации; график использует определённую версию данных; непроверенный вывод виден как черновик; renderer не загружает произвольный код/внешние данные из спецификации.

**Завершение:** критерий поставки зависит от цели. Аналитика может завершиться проверенным отчётом; ML сохраняет независимую проверку предсказаний. Итог inconclusive допустим при доказуемом ограничении данных.

**Готовность:** первый реальный аналитический отчёт с несколькими связанными блоками; job logs и точные исходники доступны из доказательств; один повреждённый блок локализован.

## Задача 7. Полное продолжение и первая alpha

**Объём:** новый вопрос после отчёта, явный выбор используемых результатов, вторая итерация, история публикаций и проверка перезапуска на границах операций.

**Проверить:** данные не профилируются повторно без причины; предыдущие выводы доступны вместе с условиями применимости; новый вопрос создаёт новый расчёт только там, где это нужно; старая публикация остаётся доступной.

**Готовность:** сценарии A–D ниже проходят вместе с регрессией ML. Доступен `0.2.0-alpha.1`; embeddings и сложный редактор не требуются для этого рубежа.

## Синтетический набор для приёмки

Использовать вымышленные данные с явной схемой: order_id, дата в согласованном часовом поясе, регион, товар, количество, выручка после скидок в RUB. Данные о возвратах подключаются отдельной версией источника.

В исходной корректной версии агрегаты заданы заранее: за август регион A — 100 000 RUB, B — 60 000 RUB; за сентябрь A — 80 000 RUB, B — 90 000 RUB. Итого 160 000 → 170 000 RUB, рост 6,25%; A снизился на 20%, B вырос на 50%.

Добавлять отдельные контролируемые варианты с дублем order_id, пропущенным регионом, новым периодом и изменённым определением метрики. Они не смешиваются с корректной исходной версией молча. Ожидаемые значения фиксируются независимо от агентского кода.

Документы содержат версию определения метрики, дату действия и источник. Вторая версия может требовать учёта возвратов, которых нет в первом датасете. Это проверяет, что модель замечает ограничение и не выдумывает пересчитанные значения.

## Сценарий A. Постановка и первый анализ

Пользователь просит объяснить изменение выручки. Если определение уже дано в применимом документе, PM использует его и показывает источник. Если выбор определения влияет на результат и не установлен, уточняет.

Техлид назначает аналитика и проверяющего. Аналитик создаёт месячные агрегаты и разбивку по регионам. Отчёт показывает общий рост и снижение региона A. Формулировка пользователя «почему упало» не заставляет систему выдумывать падение общей выручки.

Evaluator пересчитывает агрегаты по оригинальным данным. Утверждение о причине изменения требует дополнительных доказательств; сравнение периодов подтверждает динамику, а не причинность.

Приёмка: численные значения совпадают с контрольными; графики содержат период, единицы и источник; состав команды не включает обязательное обучение модели.

## Сценарий B. Следующий вопрос

После отчёта пользователь просит проверить роль скидок. PM создаёт связанную итерацию с уточнённым вопросом; передаёт прежние агрегаты, определения и их версии.

Аналитик проверяет наличие исходных цен/скидок и пригодность данных. При отсутствии необходимых полей результатом становится ограничение и запрос данных; готовые числа не подменяются догадкой.

Приёмка: первая итерация неизменна; новый вопрос имеет собственный scope; повтор того же сообщения не создаёт вторую копию итерации; существующие полезные расчёты доступны через память.

## Сценарий C. Смена определения и данных

Появляется документ с действующей новой методикой учёта возвратов. Система сохраняет обе версии, выявляет влияние на текущий вопрос и отмечает результаты, применимость которых нужно пересмотреть.

Историческая публикация продолжает показывать методику и данные, на которых она строилась. На главной странице видно, что для нового определения нужен пересчёт или новые поля.

Приёмка: старые доказательства доступны, новая методика не подставляется в старый Run, отсутствие данных о возвратах не скрывается.

## Сценарий D. Прерывание и восстановление

Остановить worker после фиксации launch intent, после завершения job до получения HTTP-ответа и после подготовки новой публикации до смены указателя.

Приёмка: job не обучает/не считает второй раз без решения; receipt сохраняется; страница показывает последнюю согласованную публикацию; расходы и незакрытые резервы не обнуляются; повторная команда возвращает исходный эффект или явно неопределённое состояние.

## Сценарий E. Поиск и точность источников

В корпусе есть одинаковые названия показателей с разными определениями и датами действия, документы другого проекта и вопрос без ответа.

Приёмка: поиск использует разрешённую область до выдачи, находит нужную версию и точные координаты, позволяет открыть контекст, не объявляет отсутствие ответа доказанным отсутствием факта. Для обзора всего документа отдельно проверяется покрытие разделов.

## Сценарий F. Страница и противоречия команд

Две команды публикуют расходящиеся оценки при разных правилах фильтрации. Редактор показывает определения и несопоставимость, техлид назначает разбор. Пользователь закрепляет один блок и меняет подпись.

Приёмка: редактор сохраняет закрепление и авторство, не присваивает проверку; обновление одной страницы с устаревшей базовой версией обнаруживает конфликт; ошибка одного графика не разрушает отчёт; старая публикация доступна.

## Как проверять

- Чистые контракты: локальные unit-проверки существенных правил без сети.
- Транзакции, миграции и конкурентные команды: отдельный PostgreSQL и изолированные временные volumes.
- Оркестрация: детерминированный адаптер модели с заранее заданными ответами и ошибками, без оплаты API.
- UI: реальные prepared data views, проверка отображения и один полный пользовательский путь.
- Retrieval: вопросы с ожидаемыми источниками/версиями, случаи без ответа и противоречия.
- Поведение LLM: отдельный контролируемый прогон с явным бюджетом; результаты оцениваются по данным и журналу, а не по уверенности текста.

## Ближайшее действие

Начать с задачи 1. Уточнения контрактов проверять на сценариях A–D до миграций; затем последовательно подключать сохранение, PM, память и динамические назначения. Статус каждой задачи обновлять по фактически выполненным изменениям, не по наличию проектного документа.
