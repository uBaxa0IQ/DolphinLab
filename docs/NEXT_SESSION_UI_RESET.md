# Следующая сессия: убрать служебный интерфейс, оставить ответы

## Последнее поручение пользователя — приоритет над прежними планами

28 октября пользователь повторно отклонил интерфейс и потребовал остановиться, зафиксировав конкретный план следующей сессии. Он НЕ хочет технические сведения даже в раскрытиях. Текущая переработка и этап 7 не приняты. Сейчас не продолжать разработку, тесты или платные прогоны.

Нужный продукт: человек загружает данные, задаёт вопрос и читает понятный ответ. Визуализация появляется, когда помогает ответить. Пользователь не должен разбираться в агентах, расчётных заданиях, проверочных протоколах или устройстве системы.

## Дополнение пользователя: свободный генератор страниц

Пользователь явно потребовал свободу модели **за пределами сборки из готовых блоков**. Редактор/генератор создаёт код и композицию исследовательской области под конкретный вопрос. Текущая схема JSON + ограниченная палитра блоков — существующая реализация, а не целевая архитектура.

- Оболочка приложения остаётся общей: навигация, материалы, чат и настройки. Генератор получает всю выделенную содержательную область, без узкого контейнера внутри неё.
- Модель может создавать собственную разметку, композицию, элементы представления и уместную интерактивность. Реализацию генерации кода (например, React/TSX с CSS) нужно спроектировать; кодовый путь ещё не реализован. Не подменять эту задачу расширением списка разрешённых карточек.
- **Конкретная стилистика обязательна:** общие шрифты, палитра, шкала отступов, размеры, типографическая иерархия, формы элементов и поведение на разных экранах. Зафиксировать их как дизайн-систему и доступный модели стилевой контракт с примерами. Готовые компоненты допустимы как помощь, но не как единственный язык представления.
- Модель сама выбирает структуру ответа и визуальное выражение: текст, таблицу, собственную диаграмму, сравнение, композицию нескольких представлений — по смыслу вопроса. Обычный вопрос по-прежнему может требовать только текстового ответа в чате.
- Код представления получает подготовленные данные и ссылки на реальные результаты. Свобода вёрстки не разрешает выдумывать значения или подменять расчёты. Выполнение представления отделить от оболочки и серверных полномочий.
- Сохранять версии сгенерированного кода, выбранных данных и представления. Следующее уточнение пользователя изменяет прежнюю работу, сохраняя историю и его правки, а не создаёт каждый раз несвязанную страницу с нуля.
- Приёмка: два разных содержательных вопроса дают разные, уместные композиции в одной стилистике; модель способна сделать представление, которого нет в фиксированном каталоге. Пользователь видит готовый ответ без названий блоков, кода и технического протокола. Проверить именно сгенерированную область на реальных результатах.

Это требование включено в следующий этап работы. Сейчас по-прежнему только фиксируем план; разработку и платные вызовы не возобновлять.

## Конкретный порядок следующей работы

1. **Удалить лишнее из пользовательского интерфейса.** Убрать примеры/демопроекты и fallback на них. Полностью убрать «Технический снимок», «Технические подробности», «Инструменты разработчика», сведения о расчётных заданиях, хешах, UUID, профилях, сжатии контекста и служебных проверках. Не переименовывать их и не переносить в очередное раскрытие. Хранение доказательств/логов остаётся на сервере; отдельный пользовательский debug-интерфейс не нужен.
2. **Сначала исправить чат.** Один вопрос → один читаемый ответ с нормальным Markdown. Удалить карточки операций, блоки «Расчёт», протокольные подтверждения подготовки, режимы сообщения, повторные плашки и дублирующий текст. Обычный вопрос получает обычный текст; график/таблица — только если помогают понять ответ. PM автоматически различает вопрос и просьбу об исследовании. Новые ответы сразу пишутся человеческим языком; оригиналы прежней переписки сохраняются в БД без публичного показа протокола.
3. **Переделать результаты как цельный ответ.** Сначала короткий вывод, затем нужные графики/таблицы и понятные ограничения. Убрать схему «одна карточка на каждый внутренний результат», повтор полного отчёта и вывода, техническую доказательную таблицу, статусы редактора и кнопки ручной сборки. Не заставлять открывать «Прочитать проверенный отчёт», чтобы узнать ответ. Редактор формирует содержательную область по работе команд, генерируя её код и композицию в рамках общей дизайн-системы. Текущий JSON-конструктор не является конечным решением. Новые числа по-прежнему требуют реального расчёта; оформление не подменяет факты.
4. **Исправить ширину и размещение.** Результаты, материалы и исследование используют всю доступную центральную область с одинаковыми отступами. Убрать узкие блоки по центру и лишние вложенные контейнеры. Проверить именно те адреса/сборки, которые видит пользователь. Материалы в целом пользователю понравились: сохранить их простой вид, убрать оставшуюся служебную информацию; заново переписывать этот экран без причины не нужно.
5. **Сократить навигацию и действия.** Оставлять на экране только то, что нужно человеку для текущей задачи. Названия — по смыслу исследования, без англицизмов и названий внутренних ролей. История/сохранённые версии остаются в данных, но не должны превращать каждый ответ в панель управления. Закрепления/заметки и вторичные функции не загромождают основной ответ; не возвращать их автоматически ради полноты старого этапа.
6. **Показать конкретный результат.** На существующих данных проверить один простой вопрос с текстовым ответом и один вопрос, которому действительно нужен график/таблица. Прочитать ответ глазами обычного пользователя. Проверить ширину и отсутствие всего удаляемого служебного содержимого. Представить 1–2 понятных экрана. Не объявлять этап 7 или весь интерфейс принятым на основании технических тестов.

## Как не расходовать лимиты впустую

- Сначала выполнить указанную чистку и переразмещение одним согласованным набором изменений. Не добавлять побочные функции, новые роли или диагностические панели вместо удаления ненужного. Свободный генератор кода представления — явно запрошенная часть работы; проектировать его отдельно от чистки интерфейса, а не заменять расширением старого конструктора.
- Не запускать повторно полный backend-набор ради правок интерфейса. Одной проверки TypeScript/сборки после пакета правок достаточно; адресные backend-проверки нужны только при изменении соответствующей логики.
- Не перезапускать исследования и не делать серию платных прогонов ради вёрстки. Уже сохранённых данных и ответов достаточно для основного UI. Настоящий редактор уже запускался; не нужно заново доказывать это перед каждой правкой.
- Проверять интерфейс по целевым сценариям; прекратить исследовать соседние функции, когда проверяемый результат виден. Скриншот нужен для демонстрации интерфейса, а не десяток разборов журналов.
- Порог остановки: **15% оставшейся пятичасовой квоты**. Недельная квота не является условием остановки.

## Критерий результата

Без объяснений разработчика понятно: какой вопрос исследуется, каков ответ, что показывает визуализация и чего пока нельзя узнать из данных. Ничего не надо раскрывать ради удаления служебного шума. Человек видит полезный ответ, а не устройство платформы.
