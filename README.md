# Dynamic ML Research Teams

Новый локальный интерфейс платформы — [Sonder workspace](apps/README.md): FastAPI, React, демопроекты и чат PM. План развития — [PLATFORM_PLAN.md](PLATFORM_PLAN.md). Интерфейс разрабатывается отдельно от конкурсного рантайма ниже; реальные вызовы модели в нём пока отключены.

Автономная система для табличных ML-задач хакатона. Все модели, метрики, разбиения, признаки, обучение и проверку пишет предоставленная LLM. В рантайме нет готового AutoML-пайплайна.

## Организация и время

Изначально существует только техлид. Он создаёт команды с вопросом исследования, целью, областью работы, исключениями и ожидаемыми артефактами. Каждая команда сразу получает тимлида, ML-инженера, Data-инженера и evaluator. Дополнительных инженеров можно подключать из фиксированного каталога. Команды можно переориентировать, завершать и архивировать; полезные результаты сохраняются.

Техлид распределяет время между направлениями. Тимлид управляет временем своей команды: назначает первый проверенный результат, следующий пересмотр, резерв проверки/refit и при необходимости явно меняет фазу. `plan_team` позволяет пересматривать план по фактическим длительностям заданий. `allocate_team_time` позволяет техлиду менять бюджет команды в пределах общего дедлайна. `plan_run` задаёт необязательную общую политику финализации.

`plan_portfolio` хранит текущую стратегию техлида и время следующего пересмотра: какие вопросы стоит исследовать независимо, какую команду переиспользовать и когда открыть новую. Число команд не задаётся сценарием. Таймаут отдельного задания можно выбирать заново; он не ограничивает следующие эксперименты. `finish(reason=...)` требует опубликованный результат, завершённые направления и отсутствие работающих заданий. Причина досрочной остановки сохраняется; публикация checkpoint сама по себе не завершает работу.

По умолчанию фиксированного деления на исследование и финализацию нет (`--reserve 0`). Единственный неизменяемый предел — общий дедлайн. Рантайм будит руководителей на выбранных ими контрольных точках и запрещает новые исследовательские задания после установленной ими границы. Уже выполняющийся код не останавливается автоматически на мягкой границе. Проверка и финализация доступны до общего дедлайна.

Тимлид и техлид не имеют инструментов записи исходников и исполнения Python. Они назначают задачи, читают доказательства, принимают организационные решения. Реализацию выполняют специалисты.

## Запуск

Нужны Python 3.12 и официальный `requirements.txt`. Рантайм ничего не устанавливает. Переменные `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL` берутся из окружения; локальный `.env` не заменяет уже заданные значения. Ключи не включаются в ZIP или контекст и удаляются из окружения вычислительных процессов.

```console
python solution.py examples/regression/task.md
python solution.py examples/multiclass_classification/task.md
```

Результат: `submission.csv` рядом с переданным `task.md`. Пути данных разрешаются относительно каталога задачи. Значения по умолчанию: 3 часа, 8 CPU, 28000 MiB бюджета заданий, до 6 одновременных обращений к модели и 25 активных агентов. Вместимость позволяет техлиду держать до шести полных команд, либо меньше команд с дополнительными инженерами. CPU/RAM остаются общими для всех направлений. Это настройки исполнения; аппаратную изоляцию процессов они не обеспечивают.

Локальный наблюдательный прогон с собственным каталогом:

```console
.venv\Scripts\python.exe solution.py path\to\task.md --seconds 900 --cpus 8 --ram-mb 8192 --work-dir test-output\live\run
```

В сборке для сдачи `reasoning_effort` по умолчанию `high`. Ни `max_tokens`, ни `max_completion_tokens` не передаются. Подтверждённое общее окно можно указать через `--context-window` / `MODEL_CONTEXT_TOKENS`; `--generation-reserve` оставляет место под reasoning и ответ, не ограничивая генерацию. Отдельные max_input/max_output из метаданных провайдера не считаются подтверждением общего окна. Общий дедлайн — 10800 секунд; последние 15 секунд предназначены для технической остановки и записи результата. Это не резерв научной финализации. Таймаут одного API-запроса — 300 секунд; таймаут Python по умолчанию — 600 секунд и выбирается агентом для конкретного задания.

## Мониторинг

`STATUS.md` в корне и каталоге запуска атомарно обновляется каждые 3 секунды. В нём обзор, стратегия техлида, состав, фокус, планы времени тимлидов, общий журнал, кандидаты, вердикты, ошибки и внизу Python-задания. Вход/выход и запросы показаны по участникам. Последний фактический вход API отделён от текущей оценки контекста; эффект сжатия записывается в байтах отдельно от неизменяемой постановки и стека.

- `events.jsonl`: сообщения, аргументы инструментов, результаты, события API и исполнения; оригинал — SQLite, зеркало восстанавливается.
- `requests/<agent_id>/`: полные запросы и ответы API без ключа доступа.
- `jobs/<job_id>/`: снимки исходников, stdout/stderr, манифест и итог процесса.
- `transcripts/<agent_id>/`: оригиналы контекста до сжатия.
- `candidates/<candidate_id>/`: замороженный CSV и хеш в реестре.
- `protocols/`, `shared/`: снимки методики оценки и передаваемых доказательств.

Прочитать состояние после окончания без активации агентов:

```console
python scripts/render_status.py path/to/run/state.sqlite3
python scripts/status.py path/to/run/state.sqlite3
```

## Сообщения и контекст

У каждого агента своя долговечная очередь. Одновременно выполняется не более одного его хода; сообщения во время запроса попадают в следующий ход. `wait` прерывается сообщением, завершением задания либо выбранным таймером.

Контекст включает исходную задачу, разрешённый стек, роль, текущий фокус, актуальную ревизию команды, участников, активные задания, методику оценки, кандидатов, последние записи общего журнала и рабочую память. Исследовательские сообщения автоматически записываются в общий журнал как сообщения, а не доказанные факты. `publish_finding` сохраняет вывод с доказательствами; evaluator может подтвердить или опровергнуть его через `assess_finding`. Техлид передаёт полезные находки другим направлениям с происхождением и снимками файлов.

Старые завершённые обмены с объёмным кодом/файлами/снимками board заменяются записями о реальных вызовах, результатах и ссылками на оригинал. Шесть последних обменов сохраняются полностью, а архивирование payload рассматривается от 16000 байт. Профилактическое смысловое сжатие требует более 128000 байт истории и обычно не менее 16 ходов; на границе завершённого этапа — не менее 12 ходов при том же объёме. Сохраняются до трёх свежих обменов, остальное сжимается отдельным вызовом той же модели. Параметры истории доступны через `--context-history-bytes` и `--context-compact-turns`. Это политика рабочей памяти, не потолок входных/выходных токенов и не увеличение физического окна модели. Проверка подтверждённой ёмкости и восстановление при context error имеют приоритет над профилактическими интервалами. Сначала сохраняется полный оригинал; неудавшееся или увеличивающее память резюме не подменяет историю. Рабочие заметки и резюме считаются навигацией, не научным доказательством. Доступен постраничный `recall`.

## Произвольный Python и проверка

`run_python` / `run_script` запускают произвольный Python специалиста в отдельном процессе. Доступны обычные библиотеки официального стека. В окружении: `TASK_ROOT`, `JOB_DIR`, `RESEARCH_CPU`. ID задания возвращается сразу; завершение будит владельца с точными путями и хвостами логов. Менеджер видит актуальный board и получает вывод от специалиста; каждое успешное диагностическое задание отдельно его не будит. Ресурсные и временные проблемы эскалируются. `wait()` без таймера ожидает событие. Потоки библиотек ограничиваются CPU-заявкой. Логи сохраняются с дисковым лимитом, доступны хвосты и постраничное чтение. Это не ограничение входа/выхода модели.

ML-инженер регистрирует реальный файл из своего направления. Замораживаются байты и SHA-256. Полезный файл из неудавшегося задания можно предложить с `allow_partial_source=true`; автоматического одобрения это не даёт. Evaluator самостоятельно запускает проверку после регистрации и фиксирует вердикт. Он проверяет методику, разбиение до обучаемых преобразований и точный финальный расчёт предсказаний. Рантайм не подменяет это встроенной метрикой.

`flag_candidate` немедленно блокирует известный дефект и уведомляет обоих руководителей. Если версия уже была опубликована, её проверенные байты сохраняются в архиве, публикация отзывается; при наличии восстанавливается другой одобренный кандидат. Первый одобренный результат автоматически становится контрольной публикацией, последующие выбирает техлид. Публикация атомарна и проверяет хеш. Наличие CSV само по себе не равно успешной доставке.

## Ошибки и восстановление

Сетевой таймаут ограничивает целый запрос. Временные ошибки повторяются с увеличивающейся задержкой. `429` учитывает Retry-After и общую паузу запросов. Ошибки ключа/модели/бюджета прекращают новые обращения. Повреждённые, пустые и обрезанные ответы не исполняются частично; оригинал сохраняется. Повторные проблемы передаются руководителю для перезапуска эпизода.

```console
python solution.py path/to/task.md --work-dir path/to/run --resume
```

`--resume` требует прежний каталог, постановку и модель. Сохраняется исходный абсолютный дедлайн, бюджет не начинается заново. OS-блокировка не допускает второй координатор. Самостоятельный supervisor задания сохраняет логи/результат даже при падении координатора. Живой процесс принимается по PID, времени создания и идентификатору владения; неизвестный запуск не повторяется автоматически. Произвольный Python не получает обещания exactly-once при аппаратном сбое. Автоматический перезапуск координатора платформой здесь не настраивается.

## Модули и проверка

Производственные файлы лежат плоско: `solution.py`, `research_config.py`, `research_runtime.py`, `research_roles.py`, `research_tools.py`, `research_timing.py`, `research_context.py`, `research_llm.py`, `research_jobs.py`, `research_worker.py`, `research_store.py`, `research_ledger.py`, `research_recovery.py`, `research_monitor.py`, `research_stack.py`. Платформа переносит корневые Python-файлы и `requirements.txt`.

```console
.venv\Scripts\python.exe -m unittest discover -s tests -v
.venv\Scripts\python.exe scripts/package.py
```

Тесты рантайма используют локальные тестовые ответы без API. Они проверяют независимую оценку/отзыв, разрешения ролей, таймауты, очереди, контекст, управление временем и восстановление после аварийного выхода координатора. Успех этих тестов не доказывает качество самостоятельных ML-решений; для этого нужны живые прогоны с аудитом исходников и доказательств.

Аудит второго прогона сохранён в `test-output/live-20261026-regression-v2/AUDIT.md`. После него исправлены ранняя остановка при активных направлениях, отсутствие сжатия у техлида, накопление старых board и лишние пробуждения менеджеров. Исправленные механизмы проходят локальные тесты; новые промпты пока не проверены дополнительным платным прогоном.

Локальная `.venv` содержит все 37 официальных верхнеуровневых версий; базовые импорты проверены. Пакеты устанавливались без транзитивных зависимостей поверх доступного окружения, поэтому полная совместимость необязательных тяжёлых библиотек пока не подтверждена.

Сборка включает только производственный Python и официальный список зависимостей. Ключи, примеры, состояния, тесты и документация не упаковываются.
